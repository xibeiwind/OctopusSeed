# 贡献与协作规范（{{PROJECT_NAME}}）

本规范约定分支、提交、Pull Request 与进度回填方式，使「需求 §编号 ↔ 工作包 Px-x ↔ 代码 [Px-x]」三层靠同一编号体系串联、可双向追溯。

> **设计前提：人机协作开发**——规范的机械劳动（读计划、回填、写文档、对齐前缀）由 AI 承担，人负责**决策**与**合并批准**。
> 本文件由 **OctopusSeed 过程模板**生成；哪些是通用内核、哪些需按本项目定制，见仓库内 `MANIFEST.md`（若已删除，见模板仓）。

---

## 1. 编号体系（单一真相源）

- **需求**：以 `docs/01-需求规格说明书.md` 的 **§章节号**（如 §18）或 **R-xx** 为稳定 ID，**不要**另行重编号。
- **工作包**：以**当前阶段执行计划**（`docs/` 下最新的 `NN-Px执行计划.md`）中的编号（如 `P0-1`）为 ID。**不在此处写死文件名**——阶段推进会换，写死会让规范随阶段推进而陈旧。
- **代码改动**：用工作包编号作提交前缀，如 `[P0-1]`。

三层通过同一套编号对齐：

```
需求(§xx)  →  工作包(Px-x，计划文档头部以「上游：§xx」声明)  →  代码([Px-x] 提交前缀 / 分支名)
```

> **编号空间说明**：`Px-y` 同时承载两类用途——**工作包**（占包位，计入 R-Plan-9 容量）与**不占包位的批次/顺带修复**（不计入容量）。提交与 PR 均须**先登记后使用**；未登记就使用的编号称「幽灵包」，由 §6 的 `registry` 校验拦截。缺口登记见 `docs/范围边界清单.md`。

> **探索区（不可判定产物的隔离带）**：结论尚不可判定的产物（可行性试探、技术死路排查）**不带编号、不进主干**——放进约定目录（如 `experiments/`，也可不建目录、只要不进主干），并**写明到期日**；到期必须给出结论：**证实 / 证伪 / 放弃**。
> 理由：**R-Plan-9** 的容量封顶只对"包"生效；探索性堆叠若以"顺便做做"的形式混进主干，它既不受容量约束、也不承担任何可回退承诺。
> **本条是无保障约定**（§8.1）：看不见、不阻断，只能靠人——**不要假装它是一条门禁**。

- **需求 ID 形态**：`§<章节号>`（如 `§3`）或 `R-<数字>`（功能）／`R-N<数字>`（非功能）——**两种后缀都有效、都不重编号**。
- **文档编号准入**：`docs/` 下**带编号**的只有"会被按编号引用或增补"的文档——`01`/`02` 基线与 `NN-Px执行计划.md`、`NN-Px-y-<主题>设计.md`、`NN-Px阶段收口评审.md`；**四份常驻单例刻意不编号**（`README.md`、`需求跟踪矩阵.md`、`项目时间线.md`、`范围边界清单.md`）——它们**唯一且稳定**，编号只会引入额外的占用与漂移维护面。引用单例时**写全名**，不得另行赋号；看板对无编号文档的编号列显示 `—`，属预期而非缺口。

## 2. 分支命名

- 格式：`Px-x-简短英文描述`（全小写、连字符分隔）。
- 示例：`P0-1-core-abstractions`、`P1-2-http-connector`。
- 从**集成分支**切出（**本仓为 `{{INTEGRATION_BRANCH}}`**）；**禁止**在 `{{INTEGRATION_BRANCH}}` / `{{RELEASE_BRANCH}}` 直接提交。
- 发布分支为 `{{RELEASE_BRANCH}}`；特性分支经 PR 合入 `{{INTEGRATION_BRANCH}}`。

---

## 3. 提交信息

- 格式：`[Px-x] 动词开头的简短描述`（中文或英文均可，保持团队一致）。
- 示例：`[P0-1] 建立核心抽象与依赖注入骨架`。
- 一个提交聚焦一个工作包；跨工作包的改动应拆分提交。
- 提交正文可附 `关联需求：§xx` 便于反向追溯。
- 该规则由 `.githooks/commit-msg` **硬校验**（§7 启用）。

## 4. Pull Request

- 标题前缀同提交：`[P0-1] 建立核心抽象`。
- 描述模板：
  - 关联工作包：P0-1
  - 关联需求：§xx
  - DoD 核对：☐ … ☐ 单测覆盖
  - 测试证据：`{{TEST_CMD}}` 结果 / 端到端说明
- 合并前需通过 `{{BUILD_CMD}}` 与 `{{TEST_CMD}}`（全绿、无新增警告）。
- **栈式 PR（stacked PR）**：当基分支是另一个**未合并**的 PR 分支时，**合并基 PR 后立即把子 PR 的 `base` 改为 `{{INTEGRATION_BRANCH}}`**，再合并子 PR——否则子 PR 的提交会落在已成历史的分支上、不进集成分支（详见 §9.1 **R-Plan-11**）。

## 5. 进度回填与文档同步（每个工作包完成即执行）

- PR 合并后，在**当前阶段执行计划**对应工作包处更新进度：
  - 工作包表建议维护 `状态`(待开始 / 进行中 / 已完成 / 阻塞 / 取消)、`依赖`、`完成日期` 列；
  - 或勾选 `§4` 中的 `- [ ] / - [x]` checklist。
- 需求状态在 `docs/需求跟踪矩阵.md`（RTM）同步更新（需求 ↔ 工作包 双向）。
- 可用 `git log --grep="[P0-1]"` 快速拉取某工作包的全部提交作为完成证据。
- **文档同步（强制，与代码同提交）**：工作包完成后必须同步下列文档，避免"代码已实现、文档仍停留在设计态"：
  1. `docs/01-需求规格说明书.md`：需求语义若因实现而细化/收敛，就地修订对应 §/R 条目，**不重编号**；
  2. `docs/02-总体设计.md`：状态机、存储 schema、接口契约、端口/端点清单与实现保持一致（发现既有描述与实现冲突时**以实现为准**并标注）；
  3. `docs/需求跟踪矩阵.md`：状态列与验收/证据列回填；
  4. 阶段计划文档：新增工作包章节（详细任务 / DoD / 测试证据 / 刻意未做）。
- **专门文档**：当工作包引入独立横切机制时，在 `docs/` 下新增 `NN-Px-y-<主题>设计.md`，由 01/02 引用；篇幅小的改动不另起文档，避免文档碎片化。

> **回填是机制的枢纽**：它保证「下一步」永远有出处，下个包开工无需重新盘点。

## 6. 质量门禁

> 下述门禁分两类：**技术栈无关**（编号 / 文档 / 单测 / 引用）与**技术栈专属**（编译期约束）。
> 专属部分由本模板的 `variants/<stack>` 提供；本仓技术栈为 **{{STACK_NAME}}**。

**栈无关门禁（本规范自带）**

- `{{BUILD_CMD}}` 全绿，**禁止新增编译器/类型检查警告**。
- `{{TEST_CMD}}` 全绿；**每个工作包至少配一个单测**，作为 DoD 的硬证据。
- **主干可运行（I1，唯一的硬不变量）**：**任意提交点**都须能用一条命令走完「构建 → 启动 → 打一次真实请求」（`{{SMOKE_CMD}}`）。它只约束**贡献价值闸门的包**；工程健壮性类（§9.5.1 Q3）不适用。**栈未提供冒烟命令时（如 `-Stack generic`）本条显式标为无保障**（§8.1 第 2 条纪律）——不要为"看起来有门禁"而交一条空过的命令。
  > 它为什么是**合并**条件而不是**开工**前提：门禁若挡在动作之前，就会制造分析瘫痪（§8.1 第 3 条）；挡在合并处，则只把"不可运行"这件事变成一次显式的取舍。
- **性能回归**：改动关键路径后复跑压测并与基线对比，结果不应显著低于基线；基线记录于专项报告。
- 构建产物（`bin/`、`obj/`、`node_modules/` 等）已在 `.gitignore`，不提交被 IDE/其它进程锁定的产物。
- **规范/文档门禁**：`tools/governance-check.ps1` 校验**六项**——① 提交信息前缀 ② 文档相对引用有效性 ③ 编号登记（幽灵包）④ **分支名携带的编号已登记**（`claim`：把"先登记后使用"的时点从提交期提前到开工期）⑤ **未定项必须有归属**（`provenance`：基线文档中的「待实测」必须指明由哪份文档 / 哪个编号定值）⑥ **热点文档大删可见**（`hotdocs`：单次提交从任一 `docs/*.md` 删除超过阈值即报）。另有 `tools/metrics.ps1 -Check` 复算过程指标并断言时间线的自动块未陈旧。全部由 CI 的 `governance` 作业执行；严格度**按测量分级**（存量合规率低时先告警、清理后提升为严格），避免历史债常红。
  > **`metrics -Check` 的例外必须写全，否则它只会一直红**：`generated_at` 与"**从 git 派生、且没有不动点**"的指标只提示、不 FAIL——它们每次复算都变，断言"未陈旧"没有意义。这是本项**唯一**的放宽，别把别的指标顺手放进去。
  > **前瞻引用的写法**（`docrefs` 用真实缺陷换来的）：指向**尚未创建**的文档时**不要带 `docs/` 路径前缀**——只写叶子文件名（如 `04-P2阶段收口评审.md`），不要写成 `docs/` 加该文件名。理由：路径式引用会被判为未解析，而"到某包才产出"的文档天然还不存在，这类引用又恰恰出现在**必写的下一步 / 开工入口**里（最容易被写）。文件创建之后，可改回带前缀的链接。这条之所以写进规范而不是只留在提交消息里：它已经踩过两次，而**一个要被人记住的规则等于没有规则**。
  > ⚠ **门禁载体失效时必须显式降级**：若 CI 的 `governance` 作业因平台原因（配额耗尽 / 被停用）不再自动执行，判据改为**合并前人工执行**，并按 §8.1 标注该项**降级为软保障**。**这是降级，不是等价替代**——人工执行不阻断他人、也不受提交时点约束。载体恢复后自动回到硬保障，期间**不得把"我跑过了"当成硬保障来叙述**。
- **看板门禁（工具门禁，与栈门禁并列、互不阻塞）**：`tools/kanban-check.ps1` 校验看板的配色 / 接线 / 几何 / 运行期不变量；**对产物运行**，故须先跑 `tools/build-kanban.ps1`。退出码 **0 通过 / 1 有 finding / 2 缺产物**；`-SkipServe` 跳过运行期检查。除上述四项，它还做**三项跨册覆盖判定**（都用**行正则独立读源文档**，**不复用会丢行的解析器**——用同一个解析器量它自己，永远量不出问题）：**登记条目全部可见**（范围边界清单 ↔ 模型）、**需求条目全部可见**（需求跟踪矩阵 ↔ 模型的 `requirements` 字段，外加"每条需求的落点必须存在"与"汇总格只许读该字段"）与**页签 ↔ 面板 1:1**（有入口打不开、或面板不可达，两种都报）。

### 6.1 本地判据**六条**（单命令入口：`tools/verify.ps1`）

> 此前文档只说"本地三证"却**从未列名**，跑哪几条、怎么跑全靠执行者记忆 —— 一个靠记忆的门禁清单本身就是漏检源。此处定死为**六条**，并收进一条命令：

| # | 判据 | 命令 |
|---|---|---|
| 1 | 构建（**含"警告数 = 0"的载体**） | `{{BUILD_GATE_CMD}}` |
| 2 | 测试 | `{{TEST_CMD}}` |
| 3 | 规范与文档 | `tools/governance-check.ps1 -Range <range> -Branch <branch> -Strict all` |
| 4 | 过程指标 | `tools/metrics.ps1 -Check` |
| 5 | 看板 | `tools/build-kanban.ps1` 然后 `tools/kanban-check.ps1` |
| 6 | **冒烟（主干可运行 I1）** | `{{SMOKE_CMD}}` |

```powershell
powershell -ExecutionPolicy Bypass -File tools/verify.ps1            # 六条全跑
powershell -ExecutionPolicy Bypass -File tools/verify.ps1 -Fast      # 只跑 3/4/5（秒级，提交前随手一跑）
```

- **退出码**：`0` 全过 / `1` 有 FAIL / `2` 无法运行（缺工具链或仓库状态异常）。
- **`UNGUARDED` 不是通过**：载体缺失（如仓库按 §10 删掉了看板工具）或命令渲染为尖括号提示（该栈没有冒烟命令）时，该项打印 **UNGUARDED** 并计入汇总——**绝不接一条空过的命令**（承 §8.1 第 2 条纪律）。"这次跑得干净"只对**真的被守卫的部分**成立。
- **刻意不 fail-fast**：六条都跑完再汇总。理由：修一条跑一次会让人放弃跑全量，而"跑全量"正是它存在的目的。
- **范围自动推断**：`-Range` 默认 `origin/{{INTEGRATION_BRANCH}}...HEAD`、`-Branch` 默认当前分支 —— 这两个参数此前靠手敲，**敲错会让门禁看起来跑了、却检了别的范围**。
- **它没有升格任何东西**：这条入口**仍只在人手动跑时才跑**，按 §8.1 是**软保障**（少的是**遗漏**，不是**阻断**）。

**栈专属门禁（本仓为 {{STACK_NAME}}）**

- 原则：**能用构建期错误表达的约束，就不要只写在文档里**（§8）。
- {{STACK_NAME}} 的具体载体（配置文件的约束、CI 作业、纪律）见本仓 `README.md` 的「栈专属门禁」一节；改动这些**载体**等于改动门禁，须走显式评审（`README.md` 与 `CONTRIBUTING.md` 同批修订）。

## 7. 本地钩子启用（把 §3 变成硬约束）

仓库内置提交信息校验钩子 `.githooks/commit-msg`，需**一次性**启用（配置存于本仓库、随仓库分发，不像默认 `.git/hooks` 不入库）：

```sh
git config core.hooksPath .githooks
```

启用后，提交信息首行不以 `[Px-x]` 开头将被**本地拒绝**。如需放宽（如临时热修），可用 `git commit --no-verify`。

> **边界说明**：钩子只校验 `[Px-x]` 的**形态**、不校验该编号**是否已登记**；后者由 CI `governance` 作业的 `registry` 检查兜底（严格项）。因此 `--no-verify` 之后仍有第二道。

## 8. 约束分层（预防 + 强制）

- **强制层（保证约束力）**：编译期错误（栈变体提供）、`.githooks/commit-msg` 钩子、CI `governance` 作业。这些在**执行点**硬性拦截，无论谁、用什么工具都绕不过。
- **预防层（减少违规）**：项目级 AI 规则（`.codebuddy/rules/*`）把编号体系、阶段计划驱动、质量门禁等内建为 AI 默认行为，但**不替代**上述硬门禁。
- **平台层**：CI 作业提供构建 / 测试 / 规范文档三线校验；若平台无分支保护能力，则约束力来自**作业本身**而非合并阻塞。

> **设计原则**：能用构建期错误表达的约束，就不要只写在文档里。**软约束会被绕过，硬约束不会。**

### 8.1 保障分层：每条约束都要能回答"它靠什么保障"

新增任何约束之前先答一个问题：**它被违反时，一个不懂上下文的人或脚本，能不能看见？能不能在执行点阻断？**

| 层级 | 判据 | 载体 | 例子 |
|---|---|---|---|
| **硬保障** | 违反即失败 | 编译错误 / git 钩子 / CI 作业 | 栈变体的编译期红线、提交前缀钩子、`governance-check` 各项（**注**：其 CI 载体若被停用，该项按 §6 的 ⚠ 条**降级为软保障**，不得按硬保障叙述） |
| **软保障** | 能看见、不阻断 | 门禁告警（warn）/ 看板健康面板 / 可复算脚本 | 计划陈旧、`hotdocs`（默认 warn）、`metrics -Check` |
| **无保障** | 看不见，只能靠人 | 明确声明为**约定或分工**，**不假装有门禁** | "这个包是否真的做完"、"谁负责回填"、度量误报的人工判定 |

**三条纪律**：

1. **能硬则硬**：能编进执行点的约束，不要只写在文档里（本节的设计原则）。
2. **不能硬就说清**：写不出机械判据的约束，必须标为**软保障或无保障**并说明判据边界——**假装有保障比没有保障更危险**，它会让人停止人工检查。
3. **避免过度硬化**：全部硬化的结果是被人**整体绕过**（`--no-verify`、直接关掉作业）。原则是**关键路径上硬、感知层面软**，并给每条新门禁留"先告警、后严格"的升级路径。

> 与 §10 ⑫ 配套：**每条新门禁必须拿一个已知缺陷撞一次**——未被撞过的门禁可能是"假守卫"（判据太松，或根本复刻不出缺陷环境）。

### 8.2 本规范自身的失效信号（软层，刻意不可机械复算）

| 信号 | 含义 | 为何不进硬层 |
|---|---|---|
| 主干连续 N（默认 5）个工作日不满足 **I1**（§6） | 主干可运行不变量名存实亡 | 需要 CI 历史；`tools/metrics.ps1` 的前提是"只从 git 复算"，两者冲突——**故明示为无保障，而不是造一个假指标** |
| 契约性设计变更未在阶段计划 §8 登记（**R-Plan-12**） | 迁移机制名存实亡 | "是否契约性"没有机械判据 |
| 收口评审连续两阶段答"什么都没删"（**R-Plan-8**） | 减法纪律退化为形式 | 同上 |

> **证伪条件**：以上任一信号出现，即判定**本节所列约束已失效**，须**重新设计**而不是"加强执行"。不接受"执行不到位"作为归因豁免——一个永远不会失败的约束，等于没有约束。

## 9. 阶段与工作包推进机制（计划驱动）

> **目的**：让「接下来做什么」**永远有唯一出处**，不依赖记忆、口头交接或跨文件检索。
> **核心原则**：**任何"下一步"若没写进文档，就等于不存在。**

### 9.1 规范条目

- **R-Plan-1 阶段必须有计划。** 每个 `Px` 阶段立项时创建 `docs/NN-Px执行计划.md`，固定骨架：
  `§0 总目标` / `§1 上游与依赖` / `§2 范围（In·Out）` / `§3 工作包全景（含依赖与关键路径）` / `§4 当前进度与下一步` / `§5 DoD 汇总` / `§6 进度记录` / `§7 刻意未做` / `§8 待决议`。（模板见 `docs/模板/阶段执行计划模板.md`。）

- **R-Plan-2 工作包完成后必更新计划。** 更新 §3 状态、§4 下一步、§6 进度记录（一行：日期 + 包号 + 内容 + PR 号）。**与 RTM 回填同批提交**，不得只更其一。

- **R-Plan-3 开工入口唯一。** 开工前先读**当前阶段执行计划**的 §3/§4；**不依赖记忆、口头交接或跨文件检索**。人与 AI 遵循同一入口。

- **R-Plan-4 依赖显式化。** §3 工作包表必须标 `依赖` 列并给出**关键路径**；被阻塞的包须写明阻塞原因与依赖项。**编号是标识、不是顺序**——顺序由依赖决定。

- **R-Plan-5 待决议集中且挂靠工作包。** 阶段内待决议集中登记于执行计划 §8，每条标注「**阻塞哪个包**」；无阻塞者可延后。

- **R-Plan-6 总纲三层不混，且上位层不复述。** 跨阶段 → `docs/01` 阶段划分；阶段内 → 阶段执行计划；包内 → 专项设计 `NN-Px-y-<主题>设计.md`。上位层引用下位层时**只给能力名 + 一句话定位 + 链接，不摘抄要点**（避免同一事实多份而漂移）。**同一事实只有一个权威处**：机械事实（门禁数字 / PR 号 / 计数 / 日期）只在**一处**写最新值——**最新值只在 `docs/项目时间线.md` §1，阶段计划只写本包增量，收口评审只写时点快照**——其余处只引用或省略；跨文档重复的机械列交由**脚本从 git 起草**（`tools/governance-check.ps1 -Timeline <前缀>`），人不手抄（摘要列刻意留人工）。

- **R-Plan-7 遗漏项单一登记。** 所有遗漏项 / 已知边界**只在 `docs/范围边界清单.md` 登记并取得编号**；专项设计、阶段计划、收口评审中的相关描述只写「见 `docs/范围边界清单.md` <编号>」，**不复述内容**（承 R-Plan-6）。每条**必须带触发条件**——答不出则标记「无触发条件」进观察区、**不入排期**。**契约级**（「本阶段不做」，红线）与**待办级**（待立项，可做）必须分开标注，不得混用。

- **R-Plan-8 摘取与关闭时点固定。** 下一阶段工作包**只在阶段收口评审时**从 `docs/范围边界清单.md` 摘取（或由明确的新需求驱动）；**执行中途不得插队**——中途出现的新需求一律入候选池。收口评审**必做三件事**：① **清算**本阶段遗漏项（全部入边界清单或显式关闭）；② 按「触发条件命中 + 价值/成本」**摘取**下阶段；③ **审视候选池**，长期无触发项**主动关闭**。
  **并在三件事之外必答两问**（各一行，不得留空）：
  - **删掉了什么**：本阶段删掉的提交 / 断言 / 抽象 / 文档。答"没有"是允许的，但**必须回答**——这是全仓**唯一的减法检查点**；没有它，结构只会单调增长（"加结构"的边际成本已被 AI 压到接近零，而"删结构"的成本没变）。
  - **设计被修订过吗**：本阶段各专项设计若一次未改，说明原因。设计是**资产**（阶段级生命周期），不是包内的一次性动作——若设计随包完成即消失，"重新设计"就没有作用对象。

- **R-Plan-9 排期容量封顶。** 阶段执行计划 §3 的工作包数量**设上限（建议 ≤8）**；超出时**必须挤掉一个**，而不是追加。**有预算才必须取舍**——这是防需求膨胀的核心约束。

- **R-Plan-10 任务分级判据（替代"重要紧急"）。** 用单一问题判定归属：「不解决则当前阶段无法继续」→ **阻塞级**（阶段计划 §8，立即决策）；「在关键路径上」→ **阶段内**（§3，已排期）；「触发条件未命中」→ **待触发**（边界清单，排队、不占注意力）。待决议与遗漏项是两类，**不得混放**。

- **R-Plan-11 栈式 PR 的合并顺序必须显式处理。** 当一个 PR 的基分支是另一个**未合并**的 PR 分支时：**基分支合并后，子 PR 的 `base` 不会自动改为集成分支**——平台仅在 base 分支被**删除**时才自动重定位。必须**先手动把子 PR 的 base 改成 `{{INTEGRATION_BRANCH}}`，再合并**；否则子 PR 的提交会落在**已成历史的分支**上、**不进集成分支**。**优先避免栈式**：依赖未合并时，从集成分支切分支并把被依赖改动**一并带上**，或等基 PR 合并后再开工（承 R-Plan-4「依赖显式化」）。

- **R-Plan-12 设计分两级，且只有契约性是"一次做对"。** 设计分**契约性**（对外接口 / 数据 schema / 持久化格式 / 协议）与**结构性**（模块划分 / 内部抽象 / 分层 / 组合方式）。判据是**改它的代价是否外溢到契约之外**——外溢即契约性。**契约性设计一次做对**，其变更**必须走显式迁移**：在阶段计划 §8 登记风险接受、给出迁移窗口到期日、到期结算（切过去并复跑主干可运行不变量，或整体回退）。**结构性设计只做到支撑本包验证即止**，超出部分记入计划 §7 刻意未做，而不是做掉。
  **不强制建造平行实现**：强制的是**承认与登记**，不是提前抽象——"必须做到可切换"会把每个包都推向"为可能不发生的替换先建一层抽象"，那正是过度设计。
  这条替代了"包内设计要一次完整"这个假设：**只有契约需要完备，结构只需要可替换**。

### 9.2 工作包推进闭环（7 步）

```
0. 开工入口：读 当前阶段执行计划 §3/§4 「当前进度与下一步」
1. 抢占编号 + 切分支：tools/claim.ps1 -Id Px-y（原子占用，已被占用即拒绝；**若该编号正由本轮登记则属"自登记"、跳过**，判据见 §9.6 第 1 条）→ git switch -c Px-y-简短英文描述
2. **最小可行设计**（R-Plan-12）：先判级别——**契约性设计一次做对**；**结构性设计只做到支撑本包验证即止**，超出部分记入 §7 刻意未做。需要则新增/更新专项设计 NN-Px-y-<主题>设计.md；该设计一旦存在，其**生命周期是阶段级**（不随本包 ✅ 而关闭），收口评审会问它是否被修订过。
3. 实施：代码 + 单测
4. 文档同步：01/02（若涉跨能力契约）、专项设计、RTM
5. 更新阶段执行计划：§3 状态 → ✅、§4 下一步、§6 进度记录   ★ 关键
6. 提交 + PR（标题同 [Px-y] 前缀）
7. 合并后 → 回到步骤 0
```

**第 5 步是机制的枢纽**：它保证"下一步"永远有出处，下个包开工无需重新盘点。

> **设计是资产，不是动作**：这是"回头重新设计"能成立的前提——若设计随包完成而消失，就没有对象可以修订，也就只剩"凭经验和感觉找一个位置"这一条路（正是本机制要消除的那种行为）。

### 9.3 状态标记

| 标记 | 含义 |
|---|---|
| ⬜ | 待开始 |
| 🔄 | 进行中 |
| ✅ | 已完成（附 PR 号） |
| ⏸ | 阻塞（注明原因与依赖项） |
| ❌ | 取消 / 转为范围外 |

**状态 → 看板泳道的映射口径**（判据按**码点**判定，所以取值必须用上表字符）：⬜→*Backlog* · 🔄→*In Progress* · ⏸→*Blocked* · ✅→*Done* · **❌→*Cancelled / out of scope***（**不得计入「待办」**；该泳道为空时不渲染）。**新增状态取值前先改这条口径与两处判据**，否则会出现"同一状态在卡片与需求点上显示不同"的偏差。

### 9.4 与既有规范的衔接

- 本机制**不替代** §5（进度回填与文档同步），而是在其之上补充**阶段级总纲与开工入口**；
- AI 协作时由 `.codebuddy/rules/stage-plan-driven/` 强制同一套路（自动读计划、自动回填）。

### 9.5 任务治理：两清单 + 三闸门

```
        新需求 / 新遗漏项
              │
        ┌─────▼──────────────────────────────────────┐
        │ 闸门① 准入三问                              │
        │   触发条件是什么？/ 归哪个阶段？/ 不做会怎样？  │
        └─────┬──────────────────────────────────────┘
              ▼
      ┌───────────────┐  闸门② 摘取（**仅阶段收口评审时**）
      │ 候选池         │  · 触发条件是否命中
      │ 范围边界清单    │  · 价值 / 成本
      └───────┬───────┘  · ★ 容量封顶：超了必须挤掉一个
              │
              ▼
      ┌───────────────┐
      │ 排期表         │  ← 阶段执行计划 §3（本阶段只做这些）
      └───────┬───────┘
              │
     【阶段执行中】WIP 限制：只跑关键路径，中途新需求一律入候选池
              │
      ┌───────▼───────┐  闸门③ 关闭（阶段收口时）
      │ 审视候选池     │  · 长期无触发 → 主动标「不做」并归档
      └───────────────┘
```

**三条口诀**：

- **候选池不设上限，排期表必须封顶**；
- **进池要答三问，出池要写触发条件**；
- **摘取只在收口时，无触发就主动关掉**。

**对应的问题与解法**：

| 问题 | 机制 |
|---|---|
| 「不能把所有待做的全放进来」 | 闸门② + **容量封顶**（R-Plan-9）：排期表超限必须取舍 |
| 「要安排重要紧急的」 | **三级判据**（R-Plan-10）替代模糊标准 |
| 「需求永远做不完」 | 闸门① 收紧入口 + 闸门③ 主动关闭清理出口 |

#### 9.5.1 艾森豪威尔矩阵（客观判据版）

「重要 / 紧急」容易退化为主观打分，因此用**两个可观测的代理指标**推导象限，**不要求任何人额外打分**：

| 维度 | **客观代理指标** | 判读 |
|---|---|---|
| **紧急** | 是否存在**阻塞关系**或明确时间点 | 阻塞某包 = 强紧急；仅触发条件而无时间压力 = 不紧急 |
| **重要** | 是否有**触发条件**，且是否贡献**价值闸门** | 有触发条件 = 有真实场景（有价值）；贡献当前阶段价值闸门 = 重要 |

| 象限 | 判据 | 载体 | 处置 |
|---|---|---|---|
| **Q1 重要 + 紧急** | 阻塞当前包，或影响交付正确性且有明确时间点 | 阶段计划 §8 待决议 / 缺陷修复 | **立即做**（优先于一切排期） |
| **Q2 重要 + 不紧急** | 贡献价值闸门，或触发条件已命中，但无时间压力 | 阶段计划 §3 排期包；边界清单「已触发」 | **计划做**（排入关键路径） |
| **Q3 不重要 + 紧急** | 有明确时间点但**不贡献产品价值**（工程债 / 节奏类） | 边界清单「工程健壮性」类 | **批量限时处理，不占主线**；能降级则降级 |
| **Q4 不重要 + 不紧急** | **无触发条件**（说不出何时做）且非价值贡献 | 边界清单「观察区」；契约级另计 | **不做 / 关闭** |

**三条判读纪律**：

1. **Q4 可自动识别**——R-Plan-7 要求"答不出触发条件 → 观察区"，因此**没有触发条件 = Q4 = 永远不会做**，应主动关闭而非挂着。
2. **Q3 最危险**——技术性任务常"看起来重要"（重构、优化、工具链），实际不贡献当前价值闸门。**唯一判据：它影响价值闸门吗？** 不影响就不许占主线。
3. **契约级（「本阶段不做」）不属于四象限**——它是**红线**，不是"不重要"，而是"不许做"，须单独标注、不得混入 Q3/Q4 而被误当待办。

**与 R-Plan-10 三级判据的关系**：三级判据（阻塞级 / 阶段内 / 待触发）是本矩阵的**投影**——阻塞级 = Q1，阶段内 = Q2，待触发 = **Q3 + Q4**。需要区分 Q3 与 Q4 时用本矩阵。

### 9.5.2 结构重构通道（给"回头改结构"一条不参与价值竞争的预算）

**它解决什么**：§9.5.1 的 Q3 把重构判为"工程健壮性类"，要求"不占主线、批量限时"。判据没错，但**重构的收益是"未来的成本降低"，不是当期价值**——因此它在闸门②的"价值 / 成本"比价里**结构性必输**。结果不是被否决，而是**根本没有出口**。

**入口判据（客观信号，复用 §9.5.1 的代理指标手法）**：命中即开一个**结构重构批次**——

| 信号 | 判据 |
|---|---|
| **抽象无第二使用者** | 一个抽象**只有一个实现，且没有任何已排期的第二个使用者** |

> **刻意只保留一条信号。** 其余候选（"同一模块被反复改动""某包实施反复延期"）在单人项目里噪声过大——频繁改动更可能来自需求变化而非结构问题。而**信号一旦误报，人就不再相信信号**：判据太松的代价不是漏报，是失效。

**三条纪律**：

1. **不占包位**：走 §1 的"不占包位批次"通道，**不进闸门②的价值 / 成本比价**；
2. **必须有验收证据**：与功能包同级——复跑主干可运行不变量（§6 **I1**）+ 一条可重放的验证；
3. **不设保底额度，但总量封顶**：有信号才开；每阶段总量**也封顶**（承 **R-Plan-9**）——保底额度会立刻变成第二个需求膨胀口。

**与 Q3 的关系**：Q3 禁止工程健壮性类**挤占主线**，本通道给它**不占主线的独立额度**。两者不冲突，而是互补：**Q3 管"不许抢"，本节管"去哪儿做"。**

### 9.6 多执行体并行（人 + 多个 AI 会话）

本规范的前提是"人 + AI"，所以真实风险不是"多人协作"，而是**同一个仓库上同时存在多个执行体**（一个人 + 若干个 AI 会话）。三条约定：

1. **编号先占后做（硬保障）**：开工前跑 `tools/claim.ps1 -Id Px-y`——它把编号写进本计划 §3 成为占位行；**若该编号已在 `docs/` 中出现即直接拒绝**（退出码 1）。于是"两个会话撞同一个编号"在**开工瞬间**暴露，而不是在评审时。CI 的 `claim` 检查用**分支名**复核同一件事（分支名是"这个包已开工"的最早可观测信号）。

   > **claim 的语义边界：自登记 ≠ 冲突。** 脚本检测的是**工作区 `docs/`**——不看 git 历史，也不区分作者是谁。因此当**本轮改动自身就是在登记该编号**（写阶段计划 §3 占位行、首次把该编号写进 RTM 或 `docs/README.md` 导航）时，它必然命中并拒绝；按上一段的字面执行就会把正常流程误判为抢号。
   > 判据因此取**命中位置是否落在本次未提交改动之外**：用 `git diff --name-only HEAD` 看被点名的文件是否都属于本轮改动 —— **全部属于 → 属自登记，跳过 claim 继续作业**；**有命中落在改动之外**（该文件本轮没碰，或已被他人合入）→ **才是真占用，换下一个空闲编号**。
   > 为什么不去改脚本：区分"自登记"需要暂存区语义与额外交互，代价高于这条注；而缺这条注的代价是**每个新项目第一次登记阶段计划时都会误解一次**（把正常流程当冲突去排查）。
2. **回填单点（无保障，靠分工）**：一个包的 §3/§4/§6 + RTM 回填**只由一个执行体执行**，即**完成最后一次提交的那个**。若两个执行体都以为对方会做，结果就是都没做——这条**没有机械判据，明确标为软约束**（§8.1）。
3. **热点文档禁止整文件重写（软保障）**：阶段计划 §3/§6、`需求跟踪矩阵.md`、`项目时间线.md` 是**并发写热点**——大改一律用**定向编辑**；确需重写前先提交现状。`hotdocs` 检查对"单次提交从任一 `docs/*.md` 删除超过阈值"报 finding：它不禁止，只让风险动作**在事故前显形**。

## 10. 过程工具（看板）

> 本节的看板工具是**只读派生视图**，不是第二真源（承 §9.1 **R-Plan-6**「同一事实只有一个权威处」）。
> **会写盘的工具只有两个，且都只写"登记"而不写"结论"**：`tools/claim.ps1`（写编号占位行，见 §9.6）与 `tools/metrics.ps1 -Write`（刷新时间线的指标自动块）。
> 门禁脚本 `governance-check.ps1` **只读，永不改文件**——"门禁"与"写盘"分离，是为了让门禁可以随时安全地跑。

**工具清单**（`tools/`）：

| 文件 | 作用 |
|---|---|
| `kanban-data.ps1` | 文档 → 看板模型的**唯一**解析点（`build` 与 `serve` 都 dot-source 它） |
| `build-kanban.ps1` | 生成**静态快照** `tools/kanban.html`；产物**不入库**（见 `.gitignore`） |
| `serve-kanban.ps1` | 本地**实时**看板（改文档后页面原地刷新；响应带 `Cache-Control: no-store`）；另提供只读 **`/docs/<name>`** 供页内抽屉取原文 |
| `kanban.template.html` | 模板**唯一**来源：静态与实时两条路径同源（`__DATA__` 占位注入） |
| `kanban-check.ps1` | 看板**配色 / 接线 / 几何 / 运行期门禁** + **三项跨册覆盖**（登记条目全部可见 / 需求条目全部可见 / 页签 ↔ 面板 1:1；都用**行正则独立读源文档**，不复用会丢行的解析器）（纯 PowerShell、无外部依赖、**对产物运行**） |
| `verify.ps1` | **本地判据单命令入口**（§6.1 的六条）：全部跑完再汇总（刻意不 fail-fast），`-Fast` 只跑 3/4/5；退出码 `0` 全过 / `1` 有 FAIL / `2` 无法运行；载体缺失或命令为占位提示时**打印 `UNGUARDED`**——**不接一条空过的命令** |
| `assets.ps1`（**由栈变体提供**，如 `.NET`） | **存量台账**（只读，**非判据**）：报"零消费者且台账未授权"的工程。**触发时点（软保障）**：任何改动解决方案 / 工程文件的工作包，提交前跑一次。**不升格为判据**的理由与撞测证据见该脚本头部（它只在增删工程时才可能报 finding，升格会把 `verify.ps1` 的秒级项变慢）。**本条没有机械判据，不得按硬保障叙述**（§8.1） |

**1) 判据依赖的文档信号 = 接口。** 看板按**结构**识别数据源（**不写死文件名**，承 R-Plan-6），因此下列形态是**接口**——改动它们等于改动看板读数，**必须同步改判据**：

| 信号 | 形态 |
|---|---|
| 工作包 | **每份**阶段执行计划的 **§3** 管道表：`\| 包 \| 内容 \| 依赖 \| 状态 \|` —— 源文档按**形态**识别（"§3 的首个数据行是包号"才是计划），且**全部阶段计划都要读**：只读最新一份会让历史阶段的包从模型里消失，它们的需求于是既不在卡片上、也不算"未映射"（覆盖判据会据此报成一串空链接）。阶段取自包号前缀，阶段筛选器的选项由这些包派生并带各自数量 |
| 待决议 | **每份**阶段执行计划的 **§8** 管道表（首列编号、末列「状态与结论」）。**决议标记须同时读编号列与状态列**——早期阶段把 ✅ 写在编号列、后期写在状态列，只读一处会把已决议项当成未决（与 §9.3 同义） |
| 需求 | `docs/需求跟踪矩阵.md` 的 `\| R-… \|` 行（含 `R-N<数字>`），且**须是 ≥7 列的宽表**（窄表另有其表）。**这张表必须连续**：解析是"从表头读到下一个 `##` 标题"的一段，中间出现空行即**读到此为止**，其下全部丢失（不同于缺口登记表"丢下一块首行"的失败方式）—— 门禁按行正则独立读并双向比对，正是为了拦住这种**不报错的静默丢失** |
| 时间线条目 | `docs/项目时间线.md` **§一** 管道表——**首列是 `YYYY-MM-DD`** |
| 阶段总览 | 同文档 **§二** 管道表——**首列是 `P<数字>`** |
| 文档清单 | `docs/*.md` 的**文件名形态**（含 `P<数字>-<数字>` = 专项设计；有 `NN-` 前缀 = 编号文档；其余 = 常驻单例）与**首行 `# 标题`**；首见 / 末改来自 **git log**（不读文件系统时间） |
| 下一步 | 当前**进行中**阶段所指计划文档的 **§4**——`## 4.` 与 `## 5.` 之间的首个 `###` 标题 + 其下要点行；**按编号定位小节、按叶子名精确匹配文件**，改名即降级为"无下一步"，不许猜 |
| 缺口登记 | `docs/范围边界清单.md`——**三张表按「列数 + 首列形态」区分**：首列 `I<数字>` 且 **6 列** = 登记表；首列 `I<数字>` 且 **4 列** = 关闭归档；首列含 `Q1~Q4` 的 **2 列**表 = 象限（**契约级红线那条没有 Q 号，须单独留一行**） |
| 状态取值 | §9.3 的五态（**按码点判定**，必须用表中字符） |
| 方案 / 设计 / 收口 | `NN-Px-y-<主题>设计.md`（文件名含**包号**）、`NN-Px阶段收口评审.md`（含**阶段号**）——工具需要它们**可机器识别**，同时**不写死具体文件名** |

**2) 只读与边界。** 看板**不回写任何文档**；拖拽重排只存浏览器 `localStorage`（个人视图）；**数据源缺失时降级为空面板**而不是崩——文档改名或尚未创建，不应让看板死掉。**文档原文只经只读端点读取**（`/docs/<name>`：单个 `.md` 叶子名、解析限定在 `docs/` 内、取不到即 404），且**转义先于结构**——文档由页面渲染，文档绝不能让看板被注入。

**3) 状态 → 泳道的映射口径**见 §9.3；`❌`（取消 / 范围外）**不得计入「待办」**，其泳道为空时不渲染。

**4) 已知缺口**（工具尚未具备的能力）**只登记在 `docs/范围边界清单.md`**（R-Plan-7），本节不复述。

**5) 维护看板时的通用禁令**（以下每条都是用真实缺陷换来的，改模板前先读）：

| # | 禁令 | 理由 |
|---|---|---|
| ① | **改配色后必须跑 `kanban-check.ps1`**；颜色只经调色板变量，两套主题**键集必须一致** | 漏定义**不报错**、只会静默回落到浅色值；对比度按 WCAG 2.1 逐对断言（文字 4.5 / 非文字 3.0），**渐变按最差色标**算 |
| ② | **重渲染必须有唯一入口**（`render()`），且**拖拽期间不得重建**；**落下列必须先清标志再渲染** | 顺序反了会被守卫吃掉；重建前后**滚动位置必须保持**（每个滚动容器都要登记进 `SCROLL_BOXES`） |
| ③ | **轮询判变更只比内容指纹**，剔除 `generatedAt` 之类每次解析都变的字段 | 比整包会让每个周期都判"变了"并整页重建，表现为「下滚一两秒后跳回顶部」 |
| ④ | **加一个视图要动四处**：面板标记、页签名表、页签按钮、渲染调度 | 漏掉**渲染调度**不会报错，只会在看板上少一块；漏掉**页签名表**更隐蔽——页签点下去静默回到工作包（`selectTab()` 把未知名字解析为 `overview`），而截图只能证明别的页签好用。四处里已有三处由门禁兜住：页签↔面板 1:1、`TAB_NAMES` ↔ 产物页签集合双向一致（`kanban-check.ps1` 的跨册覆盖项）、以及"渲染函数真的被调用"的文本断言；**面板标记**仍靠人 |
| ⑤ | **表格必须放进限高滚动盒**（`max-height` + `overflow:auto`），且该盒登记进 `SCROLL_BOXES` | 否则粘顶表头不粘、滚动位置静默丢失 |
| ⑥ | **粘顶表头必须是 `top:0`**；偏移只实测、不写死 | `top` 相对**自己的滚动盒**生效，加上页头高度会把表头推到行中间 |
| ⑦ | **页签名不得与任何元素 id 相同**（页签名就是 URL hash） | 同名 id 会让切页签被浏览器当成**页内锚点跳转**，把读者丢到面板中部 |
| ⑧ | **跳转目标必须落在存在的页签与行上**；跳转只切页签 + 滚动 + 闪烁，**不写任何状态** | 只读投影的一部分 |
| ⑨ | **外链只在能解析时才生成**（如 PR 号需要仓库地址）；取不到必须退回纯文本 | **不得凭空造链接**——要在没有 clone 元数据的机器上也能构建 |
| ⑩ | **界面语言与文档语言一致**；`tools/*.ps1` **必须 ASCII-only**（HTML/文档是 UTF-8，不受此限） | PowerShell 5.1 按本地码页解析脚本，非 ASCII 字面量会坏 |
| ⑪ | **改文档形态 = 改接口**，必须同步改解析与断言 | 见本节 1) |
| ⑫ | **门禁写完必须拿一个已知缺陷去撞一次；从未拦下过任何东西的断言，撤除而不是保留** | 前半：未被撞过的门禁可能是"假守卫"（判据太松 / 复刻不出环境）。后半：一条长期不拦截的判据不是"很安全"，是**已经烂掉了**——它只贡献安全感，不贡献信息 |
| ⑬ | **「进行中的阶段」只能取自阶段总览的 🔄 行**，不得写死阶段号（若看板进一步按阶段分区，默认展开的区块与"跳转落到未展开区块时先展开再找行"同此一条） | 写死会在阶段推进后把读者按在历史阶段上；该信号被"下一步 / 计划基准 / 文档新鲜度"共用，写死会让几处视图指向不同阶段——**同一事实只有一个权威处**（`R-Plan-6`）在看板上的投影 |
| ⑭ | **每个维度必须有明确入口**（页签 + 汇总格跳转 + 从别处的反向链接），**且计数只许读模型自己的字段**，不许在视图里就地把别的字段拼起来 | 需求此前只在卡片里（无入口、汇总格无处可跳）；而视图里的"把所有包的 `reqs` 拼起来"**不是需求清单**——一条需求映射两个包就被算两次（RTM 6 行读成 8）。入口与计数现在都有断言（`kanban-check.ps1` 的跨册覆盖三项） |

## 11. 本规范的可移植性

本规范由 **OctopusSeed** 模板生成，刻意区分了**通用内核**与**项目/技术栈专属**两部分：

- **通用内核**：编号体系、阶段计划驱动（`R-Plan-1~12`）、任务治理、文档分层、三类规范门禁、**本地判据单命令入口（§6.1）**、**人机协作交互规范（§12）**、看板工具——**可直接搬到其它项目**；
- **项目专属**：需求条目、阶段计划内容、专项设计、看板的具体配色与页签分类、技术栈构建命令；
- **技术栈专属门禁**：由 `variants/<stack>` 提供（如 {{STACK_NAME}} 的编译期约束），**核心里不写死任何语言的构建细节**。

**迁移与定制清单**见模板仓的 `MANIFEST.md`（占位符表 / 资产清单 / 定制点 / 迁移后校准 checklist）。
**改本规范时**：先判断改动属于哪一层——核心里改，各项目按需同步；项目专属处改，不要回写进规范（避免把项目内容撒进通用层）。

## 12. 人机协作交互规范（决策请求怎么做）

> **前提**：人的注意力是稀缺资源。§1 已确立分工——AI 承担机械劳动（读计划、回填、写文档、对齐前缀），**人负责决策与合并批准**。因此被抬到人面前的每一次决策，都必须**低成本、可回答、不留悬案**。
> AI 侧的执行方式见 `.codebuddy/rules/option-based-input/`；本节是人类可读的规范层。

- **R-Ask-1 决策请求一律选项化。** 凡需要用户抉择 / 输入的场合——下一步路线、方案选型、口径确认、待决议拍板、歧义澄清——必须以**结构化选项**给出，**不得**在正文用散装问句让用户自由发挥。每条选项须附**一句话后果说明**并标出**推荐项**。
- **R-Ask-2 互斥用单选、可并选用多选。** 选项之间**相互排斥**（不同策略、二选一）→ 单选；选项之间**互不冲突、可同时执行**（跑测试 / 写日志 / 更新 RTM、多个规则落点并存）→ 多选。**不得无脑单选，也不得无脑多选**——判错会让本可一次拍完的审批被切成多轮，或让互斥方案被同时选中。
- **R-Ask-3 选项不得制造幻觉入口。** 尚不存在的东西（未创建的文档、未验证的技术路径）不得作为可选依赖摆上台面。每问控制在 **2~4 个选项**；超出说明问题本身没拆干净，应先拆而非先问。
- **R-Ask-4 待决议仍以文档为真相源。** 交互层的选项只是**拍板入口**；拍板结果必须写回**当前阶段执行计划 §8**（`R-Plan-5`），并同步把 §4 的阻塞状态改为可开工。**对话里的一致 ≠ 已决议**——没写进 §8 的决议，在下一次上下文切换后即失效。
- **R-Ask-5 长期偏好必须固化。** 用户表达的跨会话偏好，至少落一处：AI 侧写 `.codebuddy/rules/`，人读侧写本文件，跨会话写长期记忆。**"说过"不等于"约定"**，未固化的偏好会在下一个会话被重新提问。

> **保障分层**（承 §8.1）：本节五条均为**软保障**——没有机械判据、不在执行点阻断，**不要假装有门禁**。它们约束的是"怎么问"，而不是"能否提交"；真正拦住动作的仍是 §6 的硬门禁与 `R-Plan` 系列。
